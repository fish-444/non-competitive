# 🌿 알로카시아 스마트팜 3D 온실

사진 + 이름을 입력하면 **Roboflow(YOLO)** 가 분석하고, **3D 온실**에 화분으로 나타나요.
화분을 클릭하면 내가 정한 이름과 분석 결과(잎 개수·겹침·새순)가 뜹니다.
센서·RAG 없이 **[사진+이름 → YOLO → 3D 반영 + 이름 커스텀]** 에만 집중한 깔끔한 단일 웹앱.

> 코딩 몰라도 돼요. 아래 순서대로 따라 하시면 됩니다.

---

## 📁 폴더 구조
```
alocasia-farm/
├── main.py              ← FastAPI 백엔드 (그룹화·원근보정·자리·잎·API)
├── crops.py             ← 작물표 — 무엇을 심었나에 따라 물·등급·빛·수확이 갈린다 (의존성 0)
├── harvest.py           ← 생장 추세 → 수확적기·생산량 예측 (crops 만 의존)
├── weather.py           ← 바깥 날씨를 재배 환경만큼만 반영 (의존성 0)
├── watering.py          ← 다음 물주기 예정일 (작물 프로필 + 흙 상태)
├── placement.py         ← 조명·그늘·통풍 계산 + 배치 최적화 (의존성 0)
├── providers/           ← 탐지기 교체 지점
│   ├── __init__.py         Detector 프로토콜 + 환경변수로 고르기
│   ├── weather_openmeteo.py  기상·토양 기본값 (키 불필요)
│   ├── weather_kma.py        기상청 단기예보 (키 필요)
│   ├── roboflow_workflow.py
│   ├── roboflow_model.py
│   ├── local_yolo.py
│   └── demo.py
├── install.ps1         ← 파워셸 한 줄 설치 (내려받기부터 전부)
├── install.bat         ← 더블클릭 설치 (이미 받아 뒀을 때)
├── uninstall.bat       ← 자동 시작 해제
├── start.bat / start.sh ← 더블클릭 실행
├── requirements.txt
├── README.md
└── static/
    ├── index.html       ← 3D 온실 + 업로드 폼 + 리스트 + 모달
    ├── three.min.js     ← 3D 라이브러리 (동봉)
    └── OrbitControls.js
```

### 탐지기 갈아 끼우기
앱의 나머지 코드는 **누가 탐지하는지 모릅니다.** 아래 하나만 지키면 됩니다.

```python
detector.detect(image) -> (boxes_px, img_area_px)
# boxes_px: [{"cls", "conf", "x1","y1","x2","y2", "area"}]  ← 이미지 픽셀
```

`providers/` 에 파일 하나 더 넣고 `providers/__init__.py:select()` 에 분기를 추가하면
로보플로우 없이 로컬 모델(HuggingFace·SAM 등)로 바꿀 수 있고, `main.py` 는 그대로입니다.

### 좌표계
네 가지가 섞이므로 변수 이름 뒤에 어느 것인지 붙입니다.

| 접미사 | 범위 | 쓰이는 곳 |
|---|---|---|
| `_px` | 0~4032 | 탐지 박스, 화면 클릭 |
| `_uv` | 0~1 | 화분 자리 저장값 (카메라와 무관) |
| `_canvas` | 0~1000 | 여러 장을 합칠 때의 공통 도화지 |
| `_cm` | −30~30 | 3D 배치, 조명 위치, 슬롯 중심 |

```
px ──(원근 변환)──> canvas ──(/CANVAS)──> uv ──(x_W − W/2)──> cm
```

### 설치 — `install.bat` 더블클릭 (이미 받아 두셨다면)
명령어를 한 줄도 안 쳐도 됩니다. 관리자 권한도 필요 없습니다.

저장소를 이미 받아 두셨다면 **`install.bat` 더블클릭**으로도 됩니다:

1. 파이썬이 있는지 확인 (없으면 어디서 받는지 알려 줍니다)
2. 필요한 패키지 설치 (1~2분)
3. `farm_env.bat` 생성 → **메모장이 열리면 `여기에_개인키` 자리에 Private API Key 를 넣고 저장**
4. 자동 시작 등록 + 바탕화면에 **`알로카시아 온실`** 바로가기 생성

이후로는:

- **컴퓨터를 켜면 서버가 알아서 뜹니다** (작업표시줄에 최소화된 창으로)
- **바탕화면의 `알로카시아 온실` 을 더블클릭**하면 브라우저가 열립니다

자동 시작을 그만두려면 **`uninstall.bat`** 을 더블클릭하세요. 자동 시작 등록과
바로가기만 지우고 `farm.db`(식물 정보)와 `farm_env.bat`(키)은 건드리지 않습니다.

> **켤 때 브라우저가 자동으로 안 열리는 게 정상입니다.** 부팅할 때마다 창이 뜨면
> 성가시니까요(`start.bat /nobrowser`). 바탕화면 바로가기로 여시면 됩니다.

### 🔑 키를 넣거나 바꾸려면 — `farm_env.bat` 편집
`farm_env.bat` 을 메모장으로 열어 이 줄만 고치시면 됩니다.

```bat
set ROBOFLOW_API_KEY=여기에_개인키
```

키는 여기서 받습니다 — **복사 아이콘**을 쓰세요. 드래그로 고르면 앞뒤가 잘리거나
공백이 딸려옵니다.

```
https://app.roboflow.com/{워크스페이스}/settings/api
```

고친 뒤 **서버를 껐다 켜야** 반영됩니다. 서버 창 맨 위 두 줄로 확인하세요:

```
[키] abcd… (20자)  ← 대시보드의 키 앞자리와 같아야 합니다
[분석 엔진] workflow · find-old-leaf-and-others
```

#### 자주 나는 실수 3가지

| 실수 | 증상 |
|---|---|
| 파워셸 습관대로 `set KEY="값"` | 배치는 **따옴표까지 키 값**으로 씁니다 |
| 붙여넣을 때 줄 끝 공백이 딸려옴 | 401 |
| 폐기한 옛 키를 다시 넣음 | `This API key does not exist (or has been revoked)` |

앞의 두 가지(따옴표·공백)는 앱이 **알아서 걷어내고** 서버 창에 `[키 경고]` 로
알려 줍니다. 그래도 파일은 고쳐 두세요.

`[키]` 줄의 앞 4자리가 대시보드에 보이는 것과 다르면 붙여넣기가 잘못된 겁니다.

### 설치 없이 그때그때 켜기
`install.bat` 없이 **`start.bat` 더블클릭**만 해도 됩니다. 서버가 뜨고 브라우저가
바로 열립니다. 대신 컴퓨터를 켤 때마다 직접 눌러 주셔야 합니다.
`farm_env.bat` 이 없으면 서버가 켜지면서 만들어 주니, 거기에 키만 넣고 다시 켜세요.

끌 때는 검은 창에서 `Ctrl+C` 또는 창 닫기.
**창을 닫으면 웹페이지는 멈추지만, 식물 정보는 `farm.db` 에 남습니다.**

> `farm_env.bat` 는 깃에 올라가지 않습니다 — 키가 새 나가지 않게 해 뒀어요.
> 맥·리눅스는 `./start.sh` (키는 `farm_env.sh` 에). `install.bat` 은 윈도우 전용입니다.
> 포트는 `FARM_PORT` 로 고정할 수 있고(`install.bat` 이 8123 으로 넣어 줍니다),
> 안 정하면 8123 이 막혔을 때 8234 → 8345 로 자동으로 넘어갑니다.

## ▶️ 실행 — 명령어로
```bash
cd 경로/non-competitive/alocasia-farm
python3 -m pip install -r requirements.txt              # 처음 한 번 (Windows: python)
python3 -m uvicorn main:app --reload --port 8123        # 서버 실행
```
브라우저에서 **http://127.0.0.1:8123** 접속.

> **`--port` 를 빼면 uvicorn 기본값인 8000 으로 뜹니다.** `start.bat` 은 8123 을
> 쓰므로, 바탕화면 바로가기(`http://localhost:8123`)로 열면 안 열립니다.
> 어느 포트로 떴는지는 uvicorn 이 시작할 때 찍어 줍니다.

> **키는 앱이 `farm_env.bat` 을 직접 읽습니다.** `start.bat` 을 안 거쳐도
> 같은 폴더에 그 파일이 있으면 알아서 불러옵니다(맥·리눅스는 `farm_env.sh`).
> 환경변수로 이미 지정한 값이 있으면 그쪽이 우선입니다.

> **`Form data requires "python-multipart" to be installed`** 로 안 뜬다면
> 설치가 중간에 끊긴 겁니다. 이것만 다시 실행하세요:
> ```bash
> python3 -m pip install fastapi "uvicorn[standard]" python-multipart pillow requests
> ```
> `ultralytics`(로컬 `.pt` 전용, torch 포함 2GB)는 로보플로우·데모만 쓰면 필요 없습니다.

## 사용법
1. 왼쪽 **① 식물 이름** 입력 (예: 프라이덱)
2. **② 무엇을 심었나요** 선택 (알로카시아 · 상추 · 바질 · 딸기 …)
3. **③ 식물 사진** 선택
4. **④ 자리 선택** (A1~E10 중 빈 자리) → **🌱 온실에 추가**
5. 3D 온실 해당 자리에 화분이 나타나고, **자리 지도**와 **리스트**에도 반영됨
6. 화분·리스트·자리 지도 **클릭** → 분석 결과 **모달**
7. 모달에서 **작물 바꾸기**, **이름 수정**, **화분 방향 회전**, **새 사진으로 갱신**, **제거** 가능

### 🌾 작물 — 같은 선반에 알로카시아 말고 다른 것도

원래 이 앱은 **알로카시아만 키운다**고 못 박혀 있었습니다. 그래서 같은 선반에
상추를 한 포기 올리면 이렇게 어긋났어요.

| 어긋난 것 | 왜 |
|---|---|
| 물주기 예정일이 5일 뒤로 | 알로카시아(습생) 간격을 그대로 썼으니까 — 상추는 이틀이면 마릅니다 |
| 캐노피 15cm 짜리 다 큰 상추가 '중품' | 알로카시아 기준치(소품 12 / 대품 22cm)로 쟀으니까 |
| 그늘로 보내도 배치 점수가 안 깎임 | 필요 광량이 알로카시아와 같다고 봤으니까 |

셋 다 코드가 틀린 게 아니라 **무엇을 심었는지 몰라서** 나던 오차입니다. 이제
화분마다 작물을 적으면 그 작물 기준으로 계산합니다.

| 작물 | 갈래 | 물 | 크기 등급 기준(캐노피) | 필요 광량 |
|---|---|---|---|---|
| 알로카시아 | 관상 | 프로필 그대로 | 12 / 22cm | 1.0 (기준) |
| 상추 · 청경채 | 잎채소 | 2~4일 | 10 / 20cm | 1.3 |
| 루꼴라 | 잎채소 | 2~4일 | 8 / 16cm | 1.3 |
| 바질 | 허브 | 2~5일 | 10 / 20cm | 1.5 |
| 딸기 | 열매채소 | 2~5일 | 12 / 22cm | 1.6 |
| 방울토마토 | 열매채소 | 2~5일 | 14 / 28cm | 1.8 |
| 고추 | 열매채소 | 2~6일 | 12 / 24cm | 1.7 |

- **작물을 바꾸면 다시 안 찍어도 등급이 다시 매겨집니다.** 등급은 절대 크기가
  아니라 '그 작물치고 큰가' 라서요. 캐노피 21cm 는 알로카시아면 아직 중품이지만
  상추면 대품입니다. 손으로 고쳐 둔 등급도 이때 덮입니다 — 기준 자체가 바뀌었으니
  예전 등급을 지키는 게 오히려 틀립니다.
- **배치 최적화가 작물을 봅니다.** 방울토마토는 알로카시아보다 빛이 1.8배
  필요하고 키도 커서 옆 화분을 크게 가립니다. 그래서 최적 배치가 토마토를 밝은
  자리로 보내고, 낮게 퍼지는 상추를 그 옆에 둡니다.
- **작물을 안 고르면 알로카시아입니다.** 예전에 등록해 둔 화분(`crop` 이 없는
  기록)도 전부 알로카시아로 읽혀서 값이 하나도 안 바뀝니다.

> ⚠️ **탐지기는 그대로입니다.** 로보플로우 워크플로는 알로카시아 잎·캐노피로
> 학습된 것이라, 상추 사진에서는 잎을 덜 잡을 수 있습니다. 작물 설정이 정하는 건
> **잡힌 박스를 어떻게 해석하는가**(등급·물·빛)뿐이고, 잎을 더 잘 잡게 하려면
> 그 작물을 학습한 모델로 갈아 끼워야 합니다(→ [탐지기 갈아 끼우기](#탐지기-갈아-끼우기)).
>
> ⚠️ 위 표의 물주기·광량 수치는 원예 통념에서 잡은 **잠정값**입니다
> (`crops.py` 의 `provisional`). 알로카시아 물주기가 그랬듯, 실제 재배 기록이
> 쌓이면 그 값으로 갈아야 합니다.

### 🌤️ 바깥 날씨 — 재배 환경만큼만 반영합니다

알로카시아 쪽은 **날씨를 일부러 안 봤습니다.** 거실 선반은 냉난방이 걸려서 바깥
기온이 잘 안 넘어오고, 여름 기준 일수만 맞으면 충분하다는 판단이었어요. 작물
온실은 전제가 다릅니다 — 비닐하우스는 바깥 기온이 거의 그대로 들어옵니다.

그래서 날씨를 보되, **얼마나 볼지는 앱이 정하지 않습니다.** 왼쪽 `🌤️ 바깥 날씨`
에서 재배 환경을 고르면 그만큼만 반영해요.

| 재배 환경 | 반영 | 비 |
|---|---|---|
| 실내 (냉난방) — **기본값** | 0% | — |
| 베란다·창가 | 45% | 안 맞음 |
| 비닐하우스·유리온실 | 80% | 안 맞음 |
| 노지 (한데) | 100% | 맞음 |

**설정을 안 건드리면 지금까지와 완전히 똑같이 동작합니다.** 위치를 안 넣으면
기상 기능 자체가 꺼져 있고, 위치를 넣어도 기본값(실내)은 반영 0% 이라 물주기·수확
숫자가 한 톨도 안 움직여요.

> 왜 이렇게까지 조심하냐면 — 에어컨을 쓰는 주택 46가구에서 실내외 기온 상관은
> 평균 r=0.42 였고 **가구별로 부호까지 갈렸습니다**(−0.24 ~ 0.92). 서울 주거
> 1년 측정에서 실내 습도는 바깥 습도와 상관이 없었고요. 그런 관계 위에 단일
> 계수를 코드에 박으면 상당수 사용자에게 계통오차가 됩니다. 사람이 선언하게
> 하는 게 정직합니다.

**어디서 받아 오나** — 기본은 [Open-Meteo](https://open-meteo.com) 로, **키도
가입도 없이** 위경도만 있으면 됩니다. 기상청 값을 쓰고 싶으면 `farm_env` 에
`KMA_SERVICE_KEY` 를 넣으세요(공공데이터포털 '단기예보 조회서비스' 의
**일반 인증키(Decoding)**). 넣으면 자동으로 그쪽으로 바뀝니다.

**무엇에 쓰나 — 둘 다 '편차'로만 씁니다.**

| | 계산 | 왜 절대값이 아니라 편차인가 |
|---|---|---|
| 물주기 | 최근 7일 증발량(ET0)이 지난달보다 몇 % 높은가 → ±일 (최대 ±2일) | 작물별 달별 간격이 **이미 계절성을 담고 있습니다**. 서울의 달별 ET0 와 그 표의 상관이 r≈0.95 예요. 절대값을 또 곱하면 계절을 두 번 셉니다 |
| 수확적기 | 앞으로 올 날씨가 **잰 기간보다** 얼마나 따뜻한가 → 배율 (0.6~1.6) | 생장 추세의 하루 증가량은 그 온실에서 실제로 찍은 사진의 기울기라 **그동안 겪은 온도가 이미 들어 있습니다**. 적산온도를 곱하면 역시 두 번이에요 |

**안 쓰는 것도 분명히 해 뒀습니다.**

- **강수** — 지붕 아래 화분에는 비가 한 방울도 안 떨어집니다. '어제 비 왔으니
  물주기 미룸' 은 관수 서비스가 흔히 하는 계산인데, 여기서는 장마철 내내 물을
  밀어 화분을 말리는 규칙이 돼요. **노지에서만** 봅니다.
- **바깥 토양수분·지온** — Open-Meteo 가 주긴 하는데(`soil_moisture_0_to_1cm`,
  `soil_temperature_0cm`), 그건 **노지 격자의 흙**이지 화분 상토가 아닙니다.
  화분은 부피가 작고 근권이 막혀 있어 마르는 속도가 아예 달라요. 화면에
  `바깥 흙 수분` 으로 참고만 띄우고 **물주기 계산에는 안 넣습니다.**
- **일사·풍속** — 실내 광량은 조명이 정하고(→ 배치 최적화), 실내 공기는 정지해
  있습니다. 바깥 값과 인과 관계가 없어요.
- **흙토람(농진청) 토양정보** — 붙이지 않았습니다. 조회에 19자리 PNU(지번코드)가
  필요해 집 주소를 받아야 하고, 그렇게 얻는 건 **그 필지 땅의 성질**이지 화분
  상토가 아닙니다. 화면에 'pH 6.9 / 배수 양호' 가 뜨면 사용자는 앱이 자기 화분을
  쟀다고 믿게 돼요.

> ⚠️ 기저온도는 작물군 세 갈래(잎채소 4°C · 허브/열매채소 10°C)로만 나눴습니다.
> 작물별 정확한 값은 문헌마다 계산법(°F·단일사인 등)까지 갈려서, 그 차이가
> 배율 하나에 묻히는 수준이라 뭉갰어요.

### 🧺 수확 — 언제 거두고 얼마나 나오나

스캔할 때마다 화분별 측정 이력(`growth_log`)이 쌓입니다. 지금까지는 '얼마나 컸나'를
그리는 데만 썼는데, **같은 기록으로 앞을 볼 수 있습니다** — 자라는 속도를 알면
목표 크기까지 며칠 남았는지가 나오니까요.

```
하루 증가량 = 지난 측정들의 기울기 (최소제곱)
수확적기     = 오늘 + (목표 크기 − 지금 크기) / 하루 증가량
생산량       = 그때의 잎 수 × 잎 한 장 무게      (잎을 따는 작물)
```

왼쪽 **🧺 수확 예정** 패널이 온실 전체를, 화분 모달의 **🧺 수확** 줄이 그 포기
하나를 보여 줍니다. 리스트에는 **오늘·이번 주에 딸 것**만 딱지가 붙습니다.

| 작물 | 수확 방식 | 기준 크기 | 한 번에 |
|---|---|---|---|
| 상추 · 청경채 | 겉잎 따기 | 캐노피 18cm | (잎 수 − 남길 5장) × 4g · 6g |
| 루꼴라 | 겉잎 따기 | 14cm | (잎 수 − 6장) × 1.5g |
| 바질 | 순 따기 | 18cm | (잎 수 − 8장) × 1g |
| 딸기 · 방울토마토 · 고추 | 열매 | 20 · 26 · 22cm | 50g · 120g · 60g **(어림)** |
| 알로카시아 | — | — | 관상이라 안 거둡니다 |

**왜 마지막 두 점의 차이가 아니라 기울기인가.** 탐지는 사진마다 들쭉날쭉합니다.
잎이 가려져 캐노피가 1cm 작게 잡힌 날 하나가 마지막 점이면, 두 점 차이로는
'줄어들었다'가 되고 수확적기가 통째로 뒤집힙니다. 여러 점에 선을 맞추면 그 한 번의
튐이 묻히고, **얼마나 잘 맞는 선인지(r²)로 신뢰도까지 말할 수 있습니다.**

모를 때는 날짜를 안 만듭니다. 근거 없는 날짜가 달력에 박히면 그걸 믿고 준비하게
되니까요.

| 이럴 때 | 이렇게 말합니다 |
|---|---|
| 측정이 한 번뿐 / 사흘도 안 벌어짐 | "아직 속도를 못 냅니다 — 며칠 뒤 다시 스캔해 주세요" |
| 안 자람 (기울기 ≤ 0) | "포기가 안 커지고 있어요 — 빛·물·자리를 먼저 살펴 주세요" |
| 이 속도면 120일 넘게 걸림 | "날짜를 찍기엔 너무 멉니다" |
| 이미 기준 크기를 넘김 | "지금이 수확적기예요" (기울기 없이도 답합니다) |

신뢰도는 **측정 횟수 · 기간 · 직선 적합도**를 함께 봅니다. 다섯 번 이상을 2주에
걸쳐 쟀고 r² 가 0.7 이상이면 `높음`, 두 번뿐이면 `낮음` 입니다.

> ⚠️ **열매는 탐지가 안 됩니다.** 모델이 잡는 건 잎과 캐노피뿐이라, 딸기·토마토·고추
> 생산량은 **포기가 기준 크기의 몇 배인지로 에두른 추정**입니다. 화면에서 `(어림)`
> 으로 표시되고, 잎채소에는 그 표시가 없습니다 — 잎은 실제로 세고 있으니까요.
> 캐노피가 세 배라고 열매가 세 배 달리지는 않으므로 두 배에서 자릅니다.
>
> ⚠️ 위 표의 기준 크기·무게도 원예 통념에서 잡은 **잠정값**입니다. 실제로 거둬서
> 재 보고 `crops.py` 의 `harvest` 를 고치면 그때부터 그 값으로 계산합니다.

### 📏 크기 등급 (소품 / 중품 / 대품)
**캐노피(포기 전체를 감싸는 박스)의 긴 변**을 실제 cm 로 재서 정합니다.

| 기준 | 환경변수 | 기본값 |
|---|---|---|
| 이하 → 소품 | `CANOPY_SMALL_CM` | 12cm |
| 이하 → 중품 | `CANOPY_LARGE_CM` | 22cm |
| 초과 → 대품 | | |

**3D 온실에 그려지는 크기도 같이 따라갑니다.** 3D 는 `top_leaf_size` 를 보는데,
원래 이 값은 '사진에서 가장 위쪽 잎' 하나의 면적으로 정했습니다. 맨 위 잎이 그
포기의 큰 잎이라는 보장이 없어서, **큰 포기인데 위쪽에 걸린 잎이 작으면 3D 에서
작게 그려졌습니다.** 캐노피를 쟀으면 그 등급을 3D 에도 그대로 물립니다.

> **왜 잎이 아니라 캐노피인가**: 잎 한 장은 포기 크기를 대표하지 못합니다.
> 큰 잎 한 장만 달린 어린 포기와, 같은 크기 잎이 여덟 장 달린 다 큰 포기가
> 같은 등급이 돼 버립니다. 캐노피는 잎 전체 퍼짐을 담고 있어서 '이 포기가
> 얼마나 큰가'에 훨씬 가깝습니다.

캐노피를 못 잡은 사진(개체 근접 촬영 등)에서는 **예전처럼 가장 큰 잎의 긴 변**으로
매깁니다. 이때 쓰는 기준치는 따로입니다.

| 기준 | 환경변수 | 기본값 |
|---|---|---|
| 이하 → 소품 | `LEAF_SMALL_CM` | 8cm |
| 이하 → 중품 | `LEAF_LARGE_CM` | 16cm |
| 초과 → 대품 | | |

선반 폭(60cm)을 아니까 박스 좌표를 cm 로 환산할 수 있습니다. 그래서
**같은 식물을 가까이 찍든 멀리서 찍든 같은 등급**이 나옵니다.
모달의 등급 칩에 `중품 · 포기 18.4cm` 처럼 실측값이 함께 뜨니, 이 값을 보고
기준치를 본인 농장에 맞춰 조정하시면 됩니다. (캐노피가 없으면 `· 잎 13.2cm` 로 뜹니다)

> 예전에는 '잎 면적 합 / 사진 전체 면적' 비율과 잎 개수로 갈랐는데,
> 농장 전체 사진에서는 개체 하나가 화면의 3~5% 뿐이라 비율 조건이 아예 발동하지
> 않고 **사실상 잎 개수만으로** 판정됐습니다. 잎 3장짜리 대엽이 잎 8장짜리
> 소엽보다 작게 나오는 문제가 있어 실측으로 바꿨습니다.
>
> 배율을 모르는 경우(개체 사진 1장을 그냥 올렸을 때)에는 예전처럼 화면 대비
> 비율로 대신 판정합니다.

### 📸 개별 사진은 '가운데 포기' 만 셉니다
개체 하나를 가까이 찍으면 프레임 안에 **옆 포기 잎이 같이 들어옵니다.** 그대로
세면 이 포기 잎이 아닌 것까지 얹혀 잎 수가 부풀고, 크기도 남의 캐노피로 매겨집니다.

그래서 개별 사진(`🌱 온실에 추가`, `📷 새 사진으로 갱신`)에서는 **사진 가운데
포기 하나만** 남깁니다:

| | |
|---|---|
| 고르는 기준 | 사진 중앙을 품은 캐노피. 없으면 중앙에서 가장 가까운 캐노피 |
| 세는 잎 | 그 캐노피 **안**에 든 잎 + **경계 바로 밖**에 붙은 잎(`CANOPY_MARGIN`) |
| 버리는 것 | 다른 캐노피와 거기 딸린 잎, 멀리 떨어진 잎 |

**캐노피를 못 잡은 사진은 예전처럼 전부 셉니다** — 고를 기준이 없는데 잘못
버리는 것보다 낫습니다.

**탑뷰 전체 사진은 정반대입니다 — 캐노피를 전부 셉니다.** 거기서는 캐노피 하나가
화분 하나라서, 하나만 남기면 나머지 포기가 통째로 사라집니다. 두 경로는 이렇게
반대로 동작하며, 테스트로 못 박아 뒀습니다
(`test_topview_keeps_every_canopy_while_a_closeup_keeps_one`).

| 사진 | 캐노피 | 잎 |
|---|---|---|
| **개별 사진** (`온실에 추가`, `새 사진으로 갱신`) | 가운데 것 **1개** | 그 캐노피 안·주변만 |
| **탑뷰 전체** (`탑뷰 사진 스캔`, `여러 장 + 원근 보정`) | **전부** (= 화분 수) | 캐노피별로 나눠서 전부 |

**겹친 캐노피의 잎을 누구 몫으로 셀지는 두 경로가 같은 규칙(`_canopy_owner`)을
씁니다.** 위 표의 차이는 '캐노피를 몇 개 남기느냐' 뿐이고, 남은 캐노피들 사이에서
잎을 가르는 방식은 동일합니다 — 갈리면 같은 사진을 어느 버튼으로 올렸느냐에 따라
잎 수가 달라지기 때문입니다 (`test_both_paths_share_the_same_ownership_rule`).

> 찍으실 때 **대상 포기를 화면 가운데**에 두세요. 가장자리에 두면 옆 포기가
> 중앙에 걸려 그쪽이 선택됩니다.

#### 무엇이 세어졌는지 사진으로 확인
개별 사진을 올리면 **모달 사진에 탐지 박스가 그려집니다.** 숫자만 보면 개수가
이상해도 어디서 틀렸는지 알 수가 없어서, 센 것과 버린 것을 함께 표시합니다.

| 색 | 뜻 |
|---|---|
| 🟧 주황 (굵게) | 캐노피 — 이 포기로 고른 박스 |
| 🟩 초록 | 성엽 |
| 🟨 노랑 | 노엽 |
| 🟦 하늘 | 새순 |
| ⬜ 흐린 회색 (얇게) | **버린 박스** — 옆 포기이거나 너무 멀어서 제외 |

개수가 이상하면 이 사진을 보고 어느 쪽인지 가르시면 됩니다:

- **잎에 초록 박스가 아예 없다** → 모델이 못 잡은 것 (사진·모델 문제)
- **초록이어야 할 잎이 흐린 회색** → 앱이 잘못 버린 것 (`CANOPY_MARGIN` 조정)
- **주황 캐노피가 엉뚱한 포기에 있다** → 대상 포기를 화면 가운데 두고 다시 촬영

### ✋ 틀린 값 직접 고치기
사진이 뭉개지거나 잎이 가려지면 탐지가 틀립니다. 모달에서 바로 고칠 수 있어요.

- **크기 등급** — 소품 / 중품 / 대품 버튼을 눌러 교체. **3D 화분 크기도 같이 바뀝니다**
  (모달 글자만 바뀌고 화면은 그대로였던 문제가 있었는데, 등급을 3D 가 보는 필드(`top_leaf_size`)에도
  같이 반영하도록 고쳤습니다).
- **잎 개수** — 단계별 `−` `+` 버튼. 잎이 하나도 안 잡힌 빈 화분(`미검출`)도 이 버튼으로
  숫자를 넣으면 **바로 3D 에 식물이 나타납니다** (빈 화분 표시가 자동으로 풀립니다).
- **단계 이동** — 성엽 `−1` + 노엽 `+1` (총 개수는 그대로)
- **자리 이동** — 🚚 자리 이동 드롭다운으로 다른 자리로 옮길 수 있습니다. 자동 배치(스캔·화분
  최근접)가 틀렸을 때, 또는 실제로 화분을 옮긴 뒤 기록만 맞출 때 씁니다. 목적지에 이미 식물이
  있으면 **서로 자리를 맞바꿉니다** — 한 자리에 둘이 앉는 일은 없습니다.

직접 고친 식물엔 **✋ 직접 수정함** 표시가 붙습니다.
`잎 유지` 모드로 스캔하면 고친 값이 보존되고, `덮어쓰기` 모드에선 새 탐지값으로 바뀝니다.

> **잎 개수를 손으로 올려 둔 만큼(보정치)은 잎 이동에도 살아남습니다.** 화분 A 의 잎이
> 2장인데 가려진 게 하나 더 있다고 보고 3으로 올려 놨다고 합시다. 그 상태에서 잡힌 잎 하나를
> 옆 화분으로 옮기면 3 − 1 = **2** 가 됩니다 — 옮긴 만큼만 깎이지, 화분에 실제로 남은 잎
> 기록 수로 통째로 다시 세지 않습니다.

- **메모** — 모달에 자유 기록 칸을 뒀습니다. 자동 판정을 고치는 게 아니라 그냥
  적어 두는 글이라(예: `잎 끝 마름 발견 · 분갈이 예정`) `✋ 직접 수정함` 표시와는
  무관합니다. 칸에서 벗어나면(blur) 자동 저장되고, 빈 칸으로 두면 메모가 지워집니다.

### 💧 물주기 · 흙 마름 표시
습도 센서가 없어서 실제 흙 수분은 모릅니다. 대신 **사람이 물 준 날짜만 기록**하고,
며칠 지났는지로 마름 위험을 보여줍니다. 모달의 `물 줬어요` 버튼을 누르면 오늘 날짜가
기록되고, 그때부터 3D 흙 색이 그 날짜를 기준으로 계산됩니다.

한 포기씩 모달을 열지 않아도, 사이드 패널의 **💧 전체 화분에 물 줬어요** 버튼을 누르면
등록된 화분 전체(잎이 안 잡힌 '미검출' 화분 포함)에 한 번에 오늘 날짜가 기록됩니다.
실제로 트레이 전체에 물을 준 뒤 한 번만 누르면 됩니다.

```
0~3일째: 흙 색 유지 (여름 기준 — 아직 괜찮음)
4일째~:  밝은 갈색으로 변함 — ⚠️ 흙 마름 위험
```

**날씨 API는 안 씁니다.** 온실 안은 냉난방으로 외부 기온 영향이 작아서, 외부 의존성과
API 키 관리를 늘리는 것보다 사람이 확인한 여름 기준 일수(3일)로 충분하다고 판단했습니다.
필요하면 `WATER_DRY_DAYS` 환경변수로 기준 일수를 조정할 수 있습니다.

흙은 이제 **잎이 있는 화분에도 항상 보입니다** (예전엔 잎이 안 잡힌 빈 화분에만 흙을
따로 그렸어요). 물 준 기록이 없는 화분은 '기록 없음'으로 표시되고 마름 경고는 뜨지 않습니다.

**📅 물주기 달력** — 사이드 패널의 📅 버튼을 누르면 월별 달력이 뜹니다. 그날 물을
받은 화분 수가 `💧숫자`로 표시되고, **날짜를 클릭하면 그날로 물주기를 기록하거나
지울 수 있습니다.**

```
날짜 클릭 → [💧 이 날짜로 전체 물주기 기록]  또는  [🗑 이 날 기록 지우기]
```

물은 줬는데 앱을 안 켠 날이 생기므로, 오늘만 기록할 수 있으면 달력이 비어 버립니다.
**지난 날짜는 뒤늦게 채울 수 있고, 잘못 누른 날은 지울 수 있습니다.**

- **미래 날짜는 막습니다.** 아직 안 준 물을 적어 두면 마름 경고가 그만큼 늦게 떠서,
  정작 필요한 날 알림이 안 옵니다
- **뒤늦게 넣어도 최근 기록이 밀려나지 않습니다.** 5일 전을 나중에 적었다고 어제 준
  기록이 사라지면 안 되니까요 — 흙 마름은 늘 **가장 최근 날짜**부터 셉니다 ‹ › 로 다른 달을 넘겨볼 수 있고, 오늘
날짜 칸은 초록 테두리로 표시됩니다. 화분마다 최근 `WATER_LOG_DAYS`일치 물준 날짜를
따로 들고 있고, 달력은 그걸 날짜별로 모아 세기만 합니다 — 별도 로그 저장소 없이
`water_log` 배열이 유일한 근거(source of truth)입니다.

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/plants/{id}/water` | 물 줬다고 기록. `day=YYYY-MM-DD`(선택, 기본 오늘) |
| DELETE | `/api/plants/{id}/water` | 그날 기록 지우기. `day=YYYY-MM-DD` (필수) |
| POST | `/api/water-all` | 화분 전체에 한 번에 기록. `day`(선택, 기본 오늘) |
| DELETE | `/api/water-all` | 그날 전체 기록 되돌리기. `day` (필수) |
| GET | `/api/water-log` | `month=YYYY-MM`(선택) — 날짜별 물 준 화분 수, 달력 렌더링용 |

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `WATER_DRY_DAYS` | `3` | 물 준 뒤 이 일수를 넘기면 흙이 마름 위험 색으로 바뀜 |
| `WATER_LOG_DAYS` | `400` | 화분마다 보관하는 물주기 기록 최대 일수 (오래된 기록은 자동 삭제) |

### 🔁 스캔 모드
스캔할 때 기존 기록을 어떻게 할지 고릅니다.

| 모드 | 동작 | 언제 |
|---|---|---|
| **잎 유지 · 새 잎만 기록** (기본) | 잎 수가 **줄어드는 건 무시**하고, 늘어난 만큼만 새 잎으로 기록 | 평소 |
| 탐지값으로 덮어쓰기 | 탐지 결과 그대로 반영 | 잎을 잘라냈을 때 |
| 전부 지우고 새로 채우기 | 등록된 식물을 모두 삭제 후 재생성 | 배치를 갈아엎었을 때 |

기본이 `잎 유지`인 이유: 탑뷰에선 큰 잎에 가려 안 잡히는 잎이 매번 달라집니다.
그대로 반영하면 어제 8장이던 식물이 오늘 5장이 돼요. 그래서 **감소는 '가려짐'으로 보고 무시**하고,
**증가분만 새 잎으로 기록**합니다. 단계 분포(새순→성엽→노엽)는 탐지가 기존만큼 잡았을 때 갱신되므로
잎이 자라는 변화는 그대로 따라갑니다.

새 잎이 나면 스캔 결과에 `새 잎 2장` 으로 표시되고, 개체별로 `leaf_log` 에 최근 30건이 쌓입니다.

### 🏡 농장 전체 사진 한 장으로 스캔
탑뷰로 농장 전체를 찍어 올리면, 잎을 **식물별로 묶어** 여러 개체를 한 번에 등록합니다.
사진 속 위치가 그대로 3D 자리로 이어져요 (사진 위쪽 = 온실 안쪽 A줄).

같은 자리에 이미 식물이 있으면 **이름과 방향은 유지한 채 상태만 갱신**되므로,
매일 같은 각도로 한 장씩 찍으면 개체가 늘어나지 않고 최신 상태로 덮어씁니다.

#### 🪴📸 화분도 이 사진에서 같이 지정
처음이거나 화분을 옮겼다면, **별도 사진 없이** 지금 스캔할 사진으로 화분 자리까지
같이 잡을 수 있습니다. `📸 탑뷰 사진 스캔` 위의 **`🪴 화분도 같이 지정`** 체크박스를
켜고 사진을 고르면:

```
사진 선택 → 선반 네 모서리 클릭 → 화분 중심 하나씩 클릭
   → [저장 후 스캔] → 화분 자리 저장 + 그 사진 그대로 스캔까지 한 번에
```

예전처럼 `🪴 화분 자리 지정`으로 **다른 사진**을 따로 찍어도 됩니다(체크박스를
안 켜면 그 흐름 그대로). 같은 사진으로 하면 모서리·화분 위치가 스캔 사진과
완벽히 일치해서 어긋날 일이 없다는 게 다릅니다.

> **모달 사진은 탑뷰 스캔에서 안 가져옵니다.** 농장 전체 사진에서 개체 하나만큼
> 잘라 낸 조각은 멀리서 찍은 사진의 일부라 흐릿하고 작습니다. 스캔으로 등록된
> 식물은 모달에 사진이 없는 채로 시작하고, 모달의 `📷 새 사진으로 갱신`으로 그
> 개체를 직접 찍어 올려야 사진이 생깁니다. 한 번 올려 두면 이후 스캔이 지나가도
> 안 지워집니다.

### 📐 여러 장 + 원근 보정 (왜곡 없는 탑뷰)
비스듬히 찍히면 위치가 밀립니다. 사진마다 **선반 네 모서리를 클릭**하면 그 왜곡을 폅니다.
2~4장으로 나눠 찍으면 해상도도 올라가고, 한 선반 좌표계로 합쳐집니다.

```
📐 여러 장 + 원근 보정  →  사진 2~4장 선택
   → 사진마다 [좌상 → 우상 → 우하 → 좌하] 순서로 모서리 클릭
   → 이 사진이 덮는 구역 선택 (전체 / 왼쪽 절반 / 우상 사분면 …)
   → 자동으로 합쳐서 등록
```

#### 🎯 모서리가 안 보일 때 — 화분을 기준점으로
케이지가 좁거나 식물이 크면 **트레이 모서리가 프레임에 안 들어옵니다.**
뒤로 물러설 공간이 없으면 구조적으로 못 담아요. 이럴 땐 모서리 대신 **화분**을 씁니다.

```
1회차: 🪴 화분 자리 지정 (트레이가 그나마 보이는 사진 1장으로)
이후:  🎯 화분 기준으로 스캔 → 아무 각도로 찍고 → 아는 화분 4개 이상 클릭
       → 클릭할 때마다 배치 지도가 뜨고, 지도에서 같은 위치를 누르면 됨
```

> 자리 이름(`C3`)만으로는 어느 화분인지 알 수 없어서, 고를 때 **저장된 배치를
> 작은 지도로** 보여 줍니다. 사진에서 찍은 화분과 같은 위치를 지도에서 누르면 돼요.
> 이미 고른 화분은 회색으로 빠집니다. 같은 지도가 왼쪽 패널에도 항상 떠 있습니다.

원근 변환은 **평면 위 대응점 4쌍**만 있으면 되고, 그게 모서리일 필요가 없습니다.
오히려 화분이 프레임 안쪽에 퍼져 있으면 외삽이 아니라 **내삽**이라 더 정확해요.
화분은 항상 잘 보이고, 안 움직이고, 헷갈리지도 않습니다.

- 기준점을 4개보다 **많이** 찍으면 최소제곱으로 클릭 오차가 평균돼 정확도가 올라갑니다
- 고른 화분이 **한 줄로 서면 안 됩니다** (넓게 퍼질수록 좋음)
- 화분 자리가 4개 이상 지정돼 있어야 버튼이 나타납니다

#### 사진을 '이어 붙이지' 않습니다
스티칭(픽셀 합성)은 이 문제에 맞지 않습니다.

| 스티칭의 문제 | |
|---|---|
| 왜곡이 안 사라짐 | 합치기는 겹친 사진을 잇는 것일 뿐, 입력이 기울어져 있으면 결과도 기울어짐 |
| 특징점 매칭 실패 | 비슷한 초록 잎이 반복되는 캐노피에서 오매칭 |
| 유령/어긋남 | 정지된 장면을 전제하는데, 잎은 촬영 사이에 움직임 |
| 무거움 | OpenCV 60MB 의존성 |

그래서 **픽셀이 아니라 결과를 합칩니다.** 사진마다 네 모서리로 원근 변환(호모그래피)을
구해 **탐지된 좌표만** 선반 좌표계로 옮기고, 겹치는 구역에서 중복 탐지를 지웁니다
(다른 사진에서 온 박스끼리 IoU > 0.5 면 같은 잎으로 보고 신뢰도 높은 쪽만 남김).

잎이 움직여도 안전하고, 특징점 매칭도 OpenCV 도 필요 없습니다.
변환 행렬은 **순수 파이썬 가우스 소거법**으로 풉니다 (의존성 추가 없음).

> 모서리 네 점이 일직선이거나 겹치면 변환을 만들 수 없어 400 으로 거부합니다.

#### 묶는 방법: 화분 + 거리 + 생김새
세 가지 신호를 함께 씁니다. 화분이 잡히면 화분 기준, 아니면 거리 기준으로 가되
**양쪽 다 '생김새'로 교정**합니다.

| 상황 | 방식 |
|---|---|
| 화분이 잡힘 | 화분 안 잎은 그 화분으로 확정 → 화분 밖으로 뻗은 잎은 **가까움 x 닮은정도**로 배정 |
| 화분이 없음 | 가까운 잎끼리 잇되 **안 닮았으면 잇지 않고**, 확실히 닮았으면 더 멀리까지 이어 줌 |

떠돌이 잎 배정에 **곱**을 쓰는 게 중요합니다. 더하기로 하면 "아주 가깝다"가
"전혀 안 닮았다"를 덮어써서, 멀리 뻗은 잎이 옆 화분에 붙어 버려요.
곱이면 둘 다 맞아야 이깁니다 (테스트로 고정: 4배 더 가까운 화분을 제치고
생김새가 같은 화분으로 갑니다).

#### 🪴 화분 자리를 미리 지정하기 (라벨링 없이)
`pot` 클래스를 라벨링하는 대신, **화분 위치를 한 번만 찍어 두면** 됩니다.
화분은 안 움직이니 이후 스캔에서 계속 재사용돼요.

```
🪴 화분 자리 지정  →  사진 1장 선택
   → 선반 네 모서리 클릭 (원근 보정용)
   → 화분 중심을 하나씩 클릭 (빈 화분도 미리 찍어 두면 나중에 심었을 때 바로 잡힘)
   → 저장 (서버가 원근 보정해서 선반 좌표로 변환)
```

**부수 효과가 더 큽니다.** 화분마다 자리(슬롯)가 고정되므로
매번 스캔해도 **"이 화분 = 항상 같은 식물"** 이 보장됩니다.
잎이 흔들리거나 카메라 각도가 달라져도 개체가 섞이지 않고, 붙여 둔 이름도 유지돼요.
(테스트로 고정: 잎을 ±45px 흔들어도 자리가 그대로입니다.)

우선순위는 **모델이 잡은 화분 → 지정해 둔 자리 → 거리+생김새** 입니다.
나중에 `pot` 클래스를 라벨링하면 지정값 없이도 자동으로 그쪽을 씁니다.

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/pots` | 지정된 화분 자리 |
| POST | `/api/pots` | `points`(정규좌표) 또는 `points_px`+`corners`(사진 픽셀) |
| DELETE | `/api/pots` | 지정 해제 |

#### 🍃 이 잎은 어느 화분 것인가 — 잎 낱개 소속
알로카시아는 잎이 화분 밖으로 멀리 뻗어서 **화분 두 개 사이에 걸친 잎**이 늘 생깁니다.
그런 잎만 골라 보여 주고 사람이 옮길 수 있게, 스캔할 때 **잎 하나하나에 기록을 남깁니다.**

소속은 **화분 실측 위치 최근접**으로 정합니다 (가까운 화분으로 반올림).
격자 칸(A1~E10)으로 매핑하지 않는 이유가 있어요 — 칸은 6 x 8 cm 인데 실제로 가장
가까운 두 화분은 **5.6 cm** 밖에 안 떨어져서, 칸으로 자르면 서로 다른 화분이 같은
칸에 들어가고 빈 칸도 잎을 받습니다. 격자는 **이름표**로만 씁니다.

거리는 **cm 로** 잽니다. 정규좌표(uv)는 가로 60 cm 와 세로 40 cm 를 똑같이 0~1 로
눌러 놓은 값이라, 그대로 재면 세로 거리가 1.5배 부풀려져요.

**애매함 판정은 1·2순위 격차**로 합니다.

```
격차(margin) = (2순위 거리 − 1순위 거리) / (2순위 + 1순위)
격차 < 0.15 → ⚠️ 애매한 잎
```

절대 거리로 자르면 화분 간격이 불규칙해서 어떤 곳은 헐겁고 어떤 곳은 빡빡합니다.
격차 비율은 간격에 알아서 맞춰져요. 생김새 교정이 최근접 판정을 뒤집은 잎도
애매한 잎으로 표시합니다 (사람이 한 번 봐 줄 만한 경우라서).

##### 끌어서 옮기기
사이드 패널의 화분 지도 아래에 **⚠️ 애매한 잎** 목록이 뜹니다.
잎을 **지도 위 화분으로 끌어다 놓거나**, 잎을 누른 뒤 화분을 누르면 소속이 바뀝니다.

옮긴 자리는 **좌표로 기억**해 둡니다. 잎에는 고유번호가 없어서 다음 스캔의 잎과
짝지을 방법이 없거든요. 대신 "그 자리에 난 잎은 이 화분 것"으로 기억해 두면
**재스캔해도 보정이 살아남습니다** (테스트로 고정). `되돌리기`를 누르면 기억을 지우고
자동 판정으로 돌아갑니다.

> **기존 ± 버튼은 그대로입니다.** 모달의 개체 단위 잎 수 수정은 예전과 똑같이 동작하고,
> 잎 기록이 없는 화분(빈 화분·예전 데이터)에서는 여전히 유일한 수정 수단이에요.

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/leaves` | 잎 낱개 + 화분별 집계. `?ambiguous=1` 이면 애매한 잎만 |
| PATCH | `/api/leaves/{leaf_id}` | `pot_slot` → 소속 화분 변경 (재스캔에도 유지) |
| DELETE | `/api/leaves/fixes` | 손으로 옮긴 기억 지우기 |

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `AMBIGUOUS_MARGIN` | `0.15` | 이보다 격차가 작으면 애매한 잎 |
| `LEAF_FIX_RADIUS_UV` | `0.03` | 손으로 옮긴 잎을 다음 스캔에서 알아보는 반경 |

#### 화분(pot) 클래스를 라벨링하면
생김새 교정을 얹어도 화분 신호가 있는 쪽이 정확합니다.

거리 기준이 약한 건 알로카시아의 생김새 때문입니다. 잎이 잎자루로 사방으로 뻗어서
**이웃 식물의 잎이 같은 식물의 잎보다 더 가까운** 상황이 흔해요.
실제 배치로 재보면 같은 식물 안 두 잎이 510px 떨어져 있는데
이웃 식물과 맞닿은 잎은 92px 로, **5배 이상 가깝습니다.**
이러면 임계값을 아무리 조정해도 갈라지지 않습니다 (테스트로 고정해 뒀어요).

그래서 로보플로우 모델에 `pot` 클래스를 추가해 라벨링하시는 걸 권합니다.
화분은 서로 겹치지 않고 **1화분 = 1식물**이라 신호가 깔끔합니다.
`object` / `pot` 처럼 잎이 아닌 클래스는 잎 개수에서 자동으로 빠집니다.

거리 기준의 민감도는 `GROUP_GAP` 로 조절합니다 (기본 `0.6`, 클수록 잘 뭉침).

#### 🍃 canopy 클래스 — 화분이 다닥다닥 붙어 잎이 심하게 겹칠 때
`pot` 앵커도 화분 밖으로 뻗은 잎까진 못 담아서, 그런 잎은 "가까움×생김새유사도"로
추측합니다. 화분이 촘촘히 붙어 잎이 서로 심하게 겹치는 트레이에서는 이 추측이
자주 틀립니다.

**`canopy`(그 식물 잎 전체를 감싸는 큰 박스) 클래스를 학습**시키면 이 추측 자체가
거의 필요 없어집니다. 화분(작음) 대신 잎 전체 퍼짐(큼)을 담아서, 잎이 화분 밖으로
뻗어 나가도 대부분 앵커 안에 들어옵니다.

**캐노피가 잡히면 규칙이 이렇게 바뀝니다 — 캐노피 하나 = 화분 하나, 그 박스 안에
든 잎 수 = 그 화분의 잎 수.** 화분 앵커와 달리 밖의 잎을 끌어다 붙이지 않습니다.
캐노피는 그 식물의 잎 전체를 담는 박스라 "밖에 있다 = 그 식물 것이 아니다"가
성립하고, 억지로 붙이면 잎 수가 부풀어 캐노피로 세는 의미가 없어지기 때문입니다.
구체적으로:

| 상황 | 처리 |
|---|---|
| 잎 중심이 캐노피 안 | 그 화분 몫으로 확정 (겹치면 중심이 가까운 캐노피) |
| **캐노피가 캐노피 안에 들어앉음** | **안쪽이 임자.** 바깥 몫에서 뺀다 — `own(바깥) = 바깥에 든 잎 − 안쪽에 든 잎` |
| 캐노피가 나란히 걸침 | **잎을 더 온전히 감싼 캐노피**가 임자. 똑같이 감쌌으면 중심이 가까운 쪽 |
| 잎 중심이 경계 바로 밖 | 제 크기의 `CANOPY_MARGIN` 배 이내면 그 화분 것 (박스가 잎 끝을 자주 자릅니다) |
| 어느 캐노피와도 멂 | 옆 화분에 얹지 않고, 그런 잎끼리 거리+생김새로 따로 묶음 |
| 캐노피는 잡혔는데 잎이 0장 | **그래도 화분으로 남김** (`미검출`). 단 확신도 `CANOPY_EMPTY_CONF` 이상일 때만 |
| 캐노피가 캐노피 안에 들어앉음 | 각각 그대로 화분 (아래 참고 — 합치지 않습니다) |
| 한 포기에 `pot` + `canopy` 동시 | 캐노피만 앵커로 씀 (안 그러면 한 식물이 둘로 쪼개짐) |

> **캐노피 안에 캐노피가 들어앉는 경우**: 포기가 다닥다닥 붙으면 작은 포기의
> 캐노피가 큰 포기 박스 안에 통째로 들어갑니다. 이때 안쪽 포기의 잎까지 바깥
> 몫으로 세면 잎 수가 부풉니다. 그래서 **집합 뺄셈**으로 처리합니다 —
> 안쪽에 든 잎은 안쪽 것이고, 바깥에서는 뺍니다. 겹침 판정(`CANOPY_NESTED_IN`,
> 기본 0.8)은 '작은 쪽이 큰 쪽에 80% 이상 덮였는가' 로 봅니다.

> **겹친 구간에서 중심 거리를 안 쓰는 이유**: 캐노피가 포기 전체를 못 감싸고
> 일부만 잡히는 일이 잦습니다. 그때 중심 거리로 고르면 **잎을 절반밖에 안 덮는
> 작은 캐노피**가 '중심이 가깝다'는 이유로 이깁니다. 실제 사진 두 장에서 잎의
> 40% 이상이 캐노피 2개 이상에 걸쳐 있었고, 중심 거리 기준은 잎을 65~88%만
> 덮는 캐노피를 고르고 있었습니다. 덮임 비율로 바꾸니 최저 덮임이 65% → 80%,
> 88% → 97% 로 올랐고 화분 수·잎 수는 그대로였습니다.

> **겹친 캐노피를 합치지 않는 이유**: "큰 박스 안에 작은 박스가 들어앉았으면 같은
> 포기를 두 번 잡은 것"으로 보고 합쳐 봤지만, 실제 추론 결과로 재 보니 손해였습니다.
> 빽빽한 트레이를 위에서 찍으면 **작은 포기의 캐노피가 큰 이웃 포기의 박스 안에
> 통째로 들어앉는 게 정상**이라, '덮였다'로는 중복 박스와 이웃 포기를 구분할 수
> 없습니다. 한 사진에서 캐노피 10개 중 5개가 이웃에 흡수돼 화분 9개가 5개로
> 줄었습니다. 같은 박스를 두 번 잡는 진짜 중복은 모델 쪽 NMS 가 이미 걸러 줍니다.

캐노피 박스 자체는 화면에 안 나옵니다 — 잎으로도 안 세고 개체로도 안 만듭니다.
묶는 앵커로만 쓰고, UI 에는 `grouped_by: canopy` 로 "캐노피로 묶었다"만 표시됩니다.

`canopy`로 묶인 무리는 그 자체로는 고정 자리 라벨이 없으므로(모델이 그 사진에서
직접 잡은 박스라 화분 자리 지정과는 별개), 무리의 무게중심을 **마크해 둔 화분 중
가장 가까운 곳**에 매칭해 자리를 정합니다 — 격자 50칸 전체가 아니라 실제로
지정해 둔 화분들 중에서만 고르므로, 마크 안 한 빈 칸에 엉뚱하게 배정되지 않습니다.
즉 `canopy`(잎 묶기) + 화분 자리 지정(고정 라벨) 을 함께 쓰는 조합이 가장 안정적입니다.

> **라벨링 난이도**: 겹침이 심한 사진일수록 캐노피 경계를 정확히 그리기도
> 어렵습니다 — 어느 잎이 어느 줄기 것인지 사람이 눈으로 구분해야 하는데, 이게
> 바로 자동화하려는 문제 그 자체라서요. 겹침이 심한 사진 위주로 학습 데이터를
> 준비하시는 걸 권합니다.

#### 🌿 잡초/풀 뭉치 클래스로 잡음 걷어내기
풀이 많이 모인 자리는 YOLO 가 그걸 잎으로 오인해서 잎 개수·그룹화가 흐트러질 수
있습니다. **로보플로우에 `weed` 같은 별도 클래스를 학습**시켜 두면, `detect_boxes()`
단계에서 탐지 직후 통째로 걸러 냅니다 — 잎 개수에도 안 들어가고, `pot` 처럼 화분
자리 신호로도 안 씁니다(잡초 뭉치를 화분처럼 취급하면 근처 잎이 그쪽으로 잘못
붙어요). 코드 쪽은 이미 준비돼 있고, 필요한 건 라벨링 + 재학습뿐입니다.

```
클래스 이름이 weed / weeds / grass 중 하나면 자동으로 걸러집니다.
다른 이름을 쓰셨다면:
```
```bash
set NOISE_CLASSES=weed,grass,debris
```

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `NOISE_CLASSES` | `weed,weeds,grass` | 탐지 직후 통째로 버릴 클래스 이름(쉼표 구분, 대소문자 무관) |
| `CANOPY_MARGIN` | `0.5` | 캐노피 경계 밖 잎을 되찾는 범위 (잎 크기 배수). 0 이면 안 되찾음 |
| `CANOPY_EMPTY_CONF` | `0.6` | 잎이 0장인 캐노피를 화분으로 인정할 최소 확신도 |
| `CANOPY_NESTED_IN` | `0.8` | 캐노피가 다른 캐노피에 이만큼 덮이면 '안에 들어앉았다'로 보고, 그 잎을 바깥에서 뺌 |

> `NON_LEAF`(`pot` 등)와는 역할이 다릅니다. `NON_LEAF` 는 화분 자리를 찾는 신호로
> 계속 쓰이고, `NOISE_CLASSES` 는 그 무엇으로도 안 쓰는 순수 잡음이라 아예 안 보이게
> 지웁니다.

#### 🎨 모양 그룹 — 비슷하게 생긴 개체끼리 묶기
품종마다 잎 모양·무늬·색이 뚜렷이 달라서, 이걸로 **같은 품종끼리 A / B / C 딱지**를 붙입니다.
떨어진 자리에 있어도 닮았으면 같은 딱지를 받아요 (리스트의 색 배지 · 모달의 칩으로 표시).

**외부 API 가 필요 없습니다.** 박스의 긴변/짧은변 비율·크기와,
잎 가운데를 잘라 낸 색(HSV 평균)만으로 로컬에서 계산합니다. 무료이고 즉시 끝납니다.

민감도는 `SHAPE_SIM` 으로 조절합니다 (기본 `0.55`, 낮출수록 잘 뭉침).

> 한계: 모양 그룹은 **품종**을 나눌 뿐 품종 **이름**은 모릅니다.
> 같은 품종을 두 화분에 키우면 둘 다 같은 딱지를 받는 게 정상이에요.
> 이름까지 자동으로 붙이고 싶다면 그때는 외부 API(Gemini 등)가 쓸모 있습니다.

### ☀️ 배치 최적화 — 어느 화분에 어느 식물을 둘까
화분 자리는 고정이고 식물은 옮길 수 있습니다. 조명·그늘을 계산해
**무엇을 어디로 옮기면 얼마나 좋아지는지**를 알려 줍니다. (팬·통풍은 안 봅니다 — 빛만.)

답이 자명하지 않은 건 **식물끼리 서로 영향을 주기** 때문이에요 —
대품을 밝은 자리에 두면 그 그늘에 옆 소품이 들어갑니다.

| 계산 | 방식 |
|---|---|
| **조도** | 조명까지 거리²반비례 × 입사각 cos. 스팟등이라 빔 반각(기본 30°) 밖은 0 |
| **그늘** | 나보다 **키 큰** 이웃의 잎우산이 덮는 넓이 (원-원 겹침). 같은 키끼리는 안 가림 |

점수는 `받은 빛 / 필요한 빛` 을 1에서 자릅니다. **넘치게 받아도 더 좋아지지 않아요** —
알로카시아는 직사광에 잎이 탑니다. 필요한 빛은 잎이 넓을수록 많습니다
(`leaf_max_cm` 실측 우선, 없으면 소중대품 등급 기본값).

#### 💡 조명 위치 조절 — 좌·우 레일 3개(2+1)
조명은 실제로 좌측·우측 레일에 3개 달려 있습니다. **레일에 고정돼 있어서
좌우(x)로는 못 옮기고, 레일을 따라(앞뒤/z)만** 조절됩니다. 3D 화면에서 분홍
조명을 끌면 그 방향으로만 움직이고, 옆으로 끌어도 레일 밖으로는 안 나갑니다.
회색 막대가 레일이에요.

기본 위치는 **화분 자리를 처음 표시할 때 찍었던 세 지점**이고,
사이드 패널에서 조명마다 좌/우 레일 전환·빔 각도·밝기를 고칠 수 있습니다.
개수는 3개로 고정입니다(레일에 물리적으로 달린 개수라 늘고 줄지 않아요).

```bash
curl -X POST localhost:8123/api/environment \
  -F 'lights=[{"side":"left","z":17,"power":1,"angle":30},
              {"side":"left","z":-13,"power":1,"angle":30},
              {"side":"right","z":2,"power":1,"angle":30}]'
```

#### 제안은 '고리'로 나옵니다
```
B7 → D3 → D9 → D6 → B2 → B7      88.6 → 94.8점 (+6.2)
```
둘씩 맞바꿔서 안 끝나는 배치가 흔합니다. 그래서 쌍이 아니라 **돌아가는 고리**로
보여 줍니다. 화분은 사람이 직접 옮기고, 다 옮긴 뒤 `✅ 화분을 옮겼어요` 를 누르면
그때 기록이 따라옵니다 — 서버가 먼저 바꿔 버리면 실제 온실과 어긋나니까요.

| POST | `/api/placement/optimize` | 최적 배치 제안 (`moves` · `cycles`) — 기록은 안 건드림 |
| POST | `/api/placement/apply` | `moves` → 실제로 옮긴 뒤 기록 반영 |
| GET | `/api/placement/heatmap` | `cols`/`rows` → 빛 격자 |
| GET·POST | `/api/environment` | 조명 실측 위치(cm) + 빔 각도 |

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `CANOPY_Y_CM` | `18` | 잎이 모인 높이 — 빛이 실제로 닿는 지점 |
| `LIGHT_ANGLE` | `30` | 조명 빔 반각(도) — 개별 조명에 `angle` 을 안 주면 이 값 |

> 최적화는 **이차 배정 문제**라 정확한 최적해를 구하려면 개체 수의 계승만큼 봐야 합니다.
> 둘씩 바꿔 보는 언덕오르기로 풉니다 — 화분 14개에 0.02초, 50개(격자 가득)에 2초입니다.

### 🗺️ 자리(슬롯) 시스템
사진만으로는 "무슨 식물인지" 구분할 수 없기 때문에, **자리로 개체를 식별**합니다.
온실 60 x 40 cm 를 **5줄 x 10칸 = 50자리** 로 나눠 `A1`~`E10` 라벨을 붙였어요 (한 칸 6 x 8 cm).

- 자리 지도에서 **빈자리 탭** → 그 자리가 자동 선택되고 이름 입력으로 이동
- 자리 지도에서 **찬 자리 탭** → 그 식물 상세 모달
- 식물 라벨은 3D 에서도 `A1 · 프라이덱` 형태로 표시

### 🎨 3D 표현 규칙
| 요소 | 색/크기 | 근거 |
|---|---|---|
| 화분 | 흰색 | 고정 |
| 새순(Shoot) | 연두 `#a4e05a` | 모델2 `shoot_count` |
| 성엽(Mature) | 녹색 `#35913c` | 모델2 `mature_count` |
| 노엽(Old) | 노랑 `#e0cf4a` | 모델2 `old_count` |
| 식물 크기 | 소엽 1.3 / 중엽 1.85 / 대엽 2.5 | `top_leaf_size` — 캐노피가 잡히면 `size_class` 와 같이 움직입니다 |

화분 방향은 모달의 **🧭 슬라이더**로 0~359° 조절되며 서버에 저장됩니다.

## 분석 엔진 (자동 선택)
| 우선순위 | 조건 | 방식 |
|---|---|---|
| 1 | `ROBOFLOW_API_KEY` + 워크플로 지정 | **로보플로우 워크플로** |
| 2 | `ROBOFLOW_API_KEY` 만 | 로보플로우 모델(YOLO) |
| 3 | `.pt` 파일 있음 | 로컬 ultralytics |
| 4 | 아무것도 없음 | 데모(모델 없이 체험) |

현재 어떤 엔진이 도는지는 화면 왼쪽 위 **`분석 엔진:`** 에 표시됩니다.

### 로보플로우로 실제 분석
```bash
ROBOFLOW_API_KEY="개인키" ROBOFLOW_MODEL_ID="find-leaf-and-object/1" python3 -m uvicorn main:app --reload
```
> **Private API Key** 사용 (공개키는 막힘). Windows PowerShell 은 `$env:ROBOFLOW_API_KEY="..."; ...`

### 모델 2개 연동 (키 하나로)
로보플로우 키 1개로 **모델 두 개**를 함께 씁니다. 각각 다른 영역에 반영돼요:

| 모델 | 환경변수 | 반영 위치 |
|---|---|---|
| **모델1** 맨 위 잎(광합성) | `ROBOFLOW_MODEL_TOP` | **3D 온실** (식물 크기·강조 잎) |
| **모델2** 새순/성숙/노령 | `ROBOFLOW_MODEL_STAGE` | **개체 특징 모달** (단계별 개수) |

```bash
ROBOFLOW_API_KEY="개인키" \
ROBOFLOW_MODEL_TOP="top-leaf-model/1" \
ROBOFLOW_MODEL_STAGE="leaf-stage-model/1" \
python3 -m uvicorn main:app --reload
```
> 두 모델을 **다르게** 지정하면 사진 1장당 추론이 2번 돌아 크레딧도 2배예요.
> 같게 두거나 하나만 지정하면 1번만 호출(재사용)해서 절약합니다.

### 🔗 로보플로우 워크플로 연동
로보플로우에서 만든 **워크플로(Workflow)** 를 통째로 호출할 수도 있어요.
모델 여러 개·전처리·필터를 로보플로우 쪽에서 조립해 두고, 이 앱은 결과만 받아 씁니다.

```bash
ROBOFLOW_API_KEY="개인키" \
ROBOFLOW_WORKSPACE="s-workspace-br86f" \
ROBOFLOW_WORKFLOW_ID="find-old-leaf-and-others" \
python3 -m uvicorn main:app --reload
```

| 환경변수 | 설명 |
|---|---|
| `ROBOFLOW_WORKSPACE` | 워크스페이스 이름 |
| `ROBOFLOW_WORKFLOW_ID` | 워크플로 ID |
| `ROBOFLOW_WORKFLOW_URL` | (선택) 전체 URL 직접 지정 — 위 두 개 대신 |
| `ROBOFLOW_WORKFLOW_IMAGE_INPUT` | (선택) 워크플로 이미지 입력 이름, 기본 `image` |

동작 방식:
- 호출 경로는 `/infer/workflows/{워크스페이스}/{워크플로}` 를 먼저 시도하고,
  404 면 `/{워크스페이스}/workflows/{워크플로}` 형식으로 한 번 더 시도합니다.
- 워크플로마다 **출력 블록 이름이 달라서** 응답 구조를 고정할 수 없어요.
  그래서 응답 전체를 훑어 박스 형태의 `predictions` 를 모두 찾아 씁니다 (중복은 1회만 계산).
- 워크플로에 **리사이즈**가 들어 있으면 좌표계가 원본과 달라지므로,
  응답에 이미지 크기가 실려 있으면 그 크기를 기준으로 잎 비율을 계산합니다.
- 워크플로는 `confidence` 파라미터를 안 받는 경우가 있어 **결과를 받은 뒤 앱에서 걸러 냅니다**
  (`CONFIDENCE`, 기본 25%).

> 워크플로 모드에서는 사진 1장당 **호출 1번**이고, 그 결과를 3D(모델1 역할)와
> 모달(모델2 역할)에 함께 씁니다. 단계 구분은 클래스 이름으로 하므로
> 워크플로가 `shoot` / `mature leaf` / `old leaf` 계열 이름을 내보내면 색이 바로 반영돼요.

## 💾 저장
식물·화분 자리·손으로 고친 값·새 잎 기록·잎 낱개 소속·조명 배치가
**`farm.db`(SQLite)** 에 남습니다.
서버를 껐다 켜도 그대로예요. 바뀔 때마다 자동 저장되고, 시작할 때 자동으로 불러옵니다.

```
[저장소] 식물 12개 · 화분자리 14개 · 잎 87장 불러옴 (farm.db)
```

| 환경변수 | 기본값 | 설명 |
|---|---|---|
| `FARM_DB` | `farm.db` | 저장 파일 경로. `""` 로 두면 저장하지 않음 |

- 백업은 `farm.db` 파일 하나만 복사하면 됩니다
- 처음부터 다시 하려면 그 파일을 지우세요
- 저장이 실패해도 서버는 계속 돕니다 (경고만 출력)
- 파일이 깨져 있으면 빈 상태로 시작합니다 — 서버가 안 뜨는 일은 없어요
