# 2. 파일이 어떻게 나뉘고 값이 어떻게 흐르나

## 파일 지도

```
alocasia-farm/
├── main.py              FastAPI 백엔드 — 그룹화·원근보정·자리·잎·엔드포인트  (3100줄)
├── crops.py             작물표: 무엇을 심었나 → 물·등급·빛·수확                (의존성 0)
├── watering.py          다음 물주기 예정일                                    (crops)
├── harvest.py           생장 추세 → 수확적기·생산량                           (crops)
├── weather.py           바깥 날씨를 재배 환경만큼만 해석                       (의존성 0)
├── placement.py         조도·그늘 계산 + 배치 최적화                          (crops)
├── providers/           바깥과 이야기하는 층 — 여기만 네트워크를 탄다
│   ├── __init__.py         Detector 프로토콜 + select() / select_weather()
│   ├── roboflow_workflow.py · roboflow_model.py · local_yolo.py · demo.py
│   ├── weather_openmeteo.py  기상·토양 기본값 (키 불필요)
│   └── weather_kma.py        기상청 단기예보 (키 필요, 격자 변환 포함)
├── static/index.html    3D 온실 + 업로드 폼 + 리스트 + 모달                   (1800줄)
├── bench_real.py        실제 사진 정확도 측정
└── test_*.py            450개, 전부 네트워크 없이
```

## 층이 나뉘는 규칙

**계산 모듈(`crops` `watering` `harvest` `weather` `placement`)은 `main` 을 안 부른다.**
그래서 FastAPI 없이, 네트워크 없이 테스트된다. 바깥에서 받아 온 값은 **인자로 받아야지
안에서 가져오면 안 된다**.

```
providers/*  ──받아옴──▶  main.py  ──인자로 넘김──▶  weather / harvest / watering
   (네트워크)              (조립)                      (순수 계산)
```

`main.py` 만 세 층을 다 안다. 예: 기상 관측은 `providers.select_weather().fetch()` 가
받아 오고, `main._weather_obs()` 가 캐시하고, `weather.water_adjust_days()` 가 해석하고,
`watering.plan_interval(..., weather_days=…)` 이 쓴다.

## ⚠️ import 순서 — 여기서 한 번 데었다

`main.py` 는 **설정을 읽은 뒤에** 우리 모듈을 import 한다.

```python
import os, re, ...            # 표준 라이브러리 — 위에
from fastapi import ...       # 외부 패키지 — 위에
...
_ensure_env_file()
_load_env_file()              # farm_env.bat/sh → os.environ

import crops                  # ← 우리 모듈은 여기부터 (noqa: E402)
import harvest, placement, providers, watering, weather
```

예전엔 이 import 들이 파일 맨 위에 있었다. 그러면 `crops` `watering` `placement`
`providers` 의 **모듈 최상단 `os.environ.get()`** 이 farm_env 를 읽기 전에 돌아서,
그 파일에 적은 값이 통째로 무시됐다. 설정 파일이 광고하던 `set CONFIDENCE=15` 가
아무 효과도 없던 게 이것이다(넣어도 25.0 이 쓰였다).

**새 환경변수를 모듈 최상단에서 읽을 거면 이 순서를 깨지 마라.** 아니면
`select_weather()` 처럼 함수 안에서 읽어라.

## 좌표계 — 네 가지가 섞인다

변수 이름 뒤에 어느 것인지 붙인다.

| 접미사 | 범위 | 쓰이는 곳 |
|---|---|---|
| `_px` | 0~4032 | 탐지 박스, 화면 클릭 |
| `_uv` | 0~1 | 화분 자리 저장값 (카메라와 무관) |
| `_canvas` | 0~1000 | 여러 장을 합칠 때의 공통 도화지 |
| `_cm` | −30~30 | 3D 배치, 조명 위치, 슬롯 중심 |

```
px ──(원근 변환)──▶ canvas ──(/CANVAS)──▶ uv ──(x_W − W/2)──▶ cm
```

선반은 60 × 40 cm, 중앙이 원점. 자리는 A1~E10 (5줄 × 10칸 = 50자리).

## 상태 — 메모리에 있고 farm.db 에 통째로 저장

| 이름 | 모양 | 무엇 |
|---|---|---|
| `PLANTS` | `{id: {...}}` | 화분마다의 모든 것 |
| `POTS` | `[{slot, u, v}]` | 미리 찍어 둔 화분 자리 (선반 uv) |
| `LEAVES` | `{leaf_id: {...}}` | 잎 낱개 — 스캔 사이에 신원을 잇는다 |
| `LEAF_FIXES` | `[{u, v, pot_slot}]` | 사람이 옮긴 잎을 **위치로** 기억 |
| `ENVIRONMENT` | `{lights: [...]}` | 조명 실측 위치(cm) |
| `SCANS` | `[{id, at, rel, plants}]` | 온실 전체 사진 이력 |
| `CALIB` | `{corners: [[u,v]×4]}` | 선반 네 모서리 — cm 배율의 기준 |
| `SITE` | `{lat, lon, site, name}` | 온실 위치 + 재배 환경 |
| `WEATHER` | 관측 캐시 | 마지막으로 받아 온 날씨 (백업엔 안 담김) |

`save_state()` 가 바뀔 때마다 통째로 쓴다(개체 수가 적어 싸다). `BACKUP_PARTS` 는
백업에 담기는 목록으로, `WEATHER` 만 빠져 있다 — 다시 받으면 되는 값이고, 담으면
복원한 순간 남의 지역 며칠 전 날씨가 '지금 날씨'로 들어앉는다.

> **복원은 통째로 갈아 끼우는 동작이다.** 파트가 없는 옛 백업을 복원하면 그 파트는
> 빈 채로 남는다. 덮기 직전 상태가 `farm-backup-이전.json` 으로 떨어져 되돌릴 수 있다.

## 화분 하나(`PLANTS[id]`)에 무엇이 들어 있나

| 갈래 | 필드 |
|---|---|
| 신원·자리 | `id` `name` `pos` `x` `z` `rot` `updated` |
| 작물 | `crop` `crop_name` |
| 모델1(맨 위 잎) | `top_leaf_size`(소엽/중엽/대엽/없음) `top_leaf_pct` |
| 모델2(단계) | `shoot_count` `mature_count` `old_count` `leaf_count` `overlap_count` `overlap_density` |
| 실측 | `canopy_cm`(포기 전체 폭) `leaf_max_cm`(가장 큰 잎) `size_class`(소품/중품/대품/미검출) |
| 물 | `water_log[]` `last_watered` `soil`(건조/일반/과습) + 계산값 `days_since_watered` `next_water` `days_until` `interval_days` `basis` `soil_dry` |
| 이력 | `growth_log[]`(하루 한 줄: `on` `src` `canopy_cm` `leaf_max_cm` `leaf_count` `size_class` `photo`) `photo_log[]` `leaf_log[]` |
| 수확(계산값) | `harvest_on` `harvest_days` `harvest_g` `harvest_ready` |
| 기타 | `manual`(손으로 고침) `empty`(잎 미검출) `note` `thumb` `photo` |

`growth_log` 가 수확 예측의 재료다 — 스캔할 때마다 한 줄씩 쌓이고, 같은 날 여러 번
찍으면 그날 마지막 것으로 갱신된다.

## 작물표 (`crops.py`)

작물이 정하는 건 다섯 가지다.

| 항목 | 필드 | 쓰는 곳 |
|---|---|---|
| 물주기 달별 간격 | `water.by_month` | `watering.profile_for` |
| 등급 기준치 | `canopy_cm` `leaf_cm` | `main.grade_by_*` |
| 필요 광량 배수 | `light` | `placement._need_light` |
| 폭 대비 키 · 무엇으로 재나 | `height_ratio` `radius_from` | `placement.plant_shape` |
| 수확 규격 | `harvest` | `harvest.forecast` |

작물: 알로카시아(관상, 기본) · 상추 · 청경채 · 루꼴라 · 바질 · 딸기 · 방울토마토 · 고추.

**기본 작물(알로카시아)은 일부러 `water` 를 비워 뒀다.** `water_profile.json`(또는
`watering.DEFAULT_PROFILE`)이 이미 알로카시아 기준이라, 작물표에 또 적으면 두 벌이
갈라진다. 등급 기준치도 환경변수(`CANOPY_SMALL_CM` 등)를 그대로 물려받는다.

## 재배 환경 (`weather.py`)

바깥 날씨가 화분까지 얼마나 넘어오는가. 이 계수 하나가 기상 보정 전체의 세기다.

| 환경 | 반영 | 비를 맞나 |
|---|---|---|
| `indoor` 실내 (냉난방) — **기본** | 0% | 아니오 |
| `veranda` 베란다·창가 | 45% | 아니오 |
| `greenhouse` 비닐하우스·유리온실 | 80% | 아니오 |
| `outdoor` 노지 | 100% | 예 |

기본이 0% 이라, 위치를 넣어도 설정을 안 바꾸면 물주기·수확 숫자가 안 움직인다.
